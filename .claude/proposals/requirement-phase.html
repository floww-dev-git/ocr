The Requirement Phase

Intake, triage, and the PRD contract — the front of the pipeline, where a thin human intent becomes a scoped, falsifiable set of stories. It runs in two phases split at concept lock: Phase 1 · Concept (product — manager + user) settles what to build; Phase 2 · Contract (manager-owned end to end) expresses it as three separate artifacts — PRD → user flows → user stories — at capability altitude. Code-level depth (impact analysis, escalation checks, the scope fence) belongs to Design, where the architecture is actually known. Read outside-in: the phase's law → the intake rail → the artifacts & review surface → the PRD contract → the failure modes.

A requirement is a delta on the module graph; the PRD is a transformation, never a creation. Thin input produces questions back at the human, not a padded document. The agents contribute structure, gap-detection, and codebase grounding — never requirements. Anything that would propagate verbatim downstream should die here.

1 The intake rail — two phases, split at concept lock

Eight stations across two phases carry a requirement from a doc (or a sentence) to approved stories. Phase 1 · Concept (product — manager + user) turns thin intent into a locked concept; Phase 2 · Contract (manager-owned end to end) expresses it as three artifacts — PRD ◆1a → flows ✓ → stories ◆1b — each pass reviewed on a living HTML review page (section 2). No code reading anywhere in Phase A: the PRD names key modules as candidates, honestly labeled; verification happens in Phase B where design authority lives. M = manager (the WHAT); A = architect (enters at dispatch). Tap any step for what it does, what it changes downstream, and its status.

Phase 1 · Conceptproduct — manager + user. Thin intent → a locked concept, before any architect or code audit.
1 · Understand & groundM/intake-requirement 1–2exists today

Two beats. Scan → validate: a cheap pass over the app map and CLAUDE.md titles yields a candidate module list, confirmed with the user before any deep reading — a 5-second veto beats a 5-minute wrong read. Then ground: full conceptual depth on the confirmed set only — problem, domain terminology, what those modules can do today (capability layer: app CLAUDE.mds, domain docs, existing flows), never the code structure. The structural caller/parity audit defers to Phase 2, paid once, on the locked concept.

2 Three artifacts, one living review surface proposed

A gate is only as strong as the reviewer's comprehension at it. A wall-of-markdown PRD gets skimmed; a skimmed gate is a rubber stamp; and a rubber-stamped Gate 1 sets wrong direction at the exact moment it's cheapest to fix. So artifact form is gate integrity, not cosmetics. Markdown stays canonical (agents parse it downstream for the feature's whole life); the HTML is the human review rendering — regenerated from the md, never hand-drifted.

The artifact chain (markdown — canonical)
  • <app>/docs/prd/PRD-<slug>.md — WHAT & WHY, broad: problem · JTBD · value proposition · outcome · scope · actors · key modules (candidates)
  • <app>/docs/user_stories/<slug>/flows.md — actor journeys, step by step, diagram-first
  • <app>/docs/user_stories/<slug>/stories.md — GWT cards, each citing the flow step it serves

Three separate files, three altitudes — a PRD edit never silently rewrites flows; a flow edit never silently rewrites stories. Each derives from the one before, at its own review beat.

The review surface (HTML — what the human sees at the gates)
  • ONE living page per feature that grows pass by pass: PRD → +flows → +stories — the reviewer always returns to the same place and sees the phase's state
  • Flows drawn as actual diagrams (actor → step → outcome), stories as cards grouped under the step they serve
  • UNCONFIRMED / open questions visually flagged — impossible to miss
  • On iteration: what-changed-since-your-last-review highlighted
  • Frontend-design bar: progressive disclosure, no walls of text — same discipline as the architect's /module-blueprint, applied to the requirement side
  • Lifespan: alive until the feature is delivered — the feature's readable face for its whole life; retired with the worktree at delivery
The pattern already exists on the architect's side — /module-blueprint is exactly this for Phase B (interactive HTML, read outside-in, confirmed pass-by-pass). This gives the manager's gates the same treatment: a consistent review experience at every gate, both phases.

Four classes board the rail at four depths. The under-classing detector moved with the depth: the architect at Phase-B entry runs the escalation checks and can send a class 2 back up to class 1 — with code evidence. The escalation protocol — class 2 → class 1

Class 2 is the majority lane, so its escape hatch must be a free check: all six triggers are facts the architect's Phase-B impact analysis already computes — running them at PRD time would demand code reading the phase deliberately doesn't do. Any one trips → bounce back via the Design Correction Protocol → up-class. This is the REF-001 net — "extend transitions to other entities" that was really an engine, ~60% of live behaviour described, 14 behaviours missed.

Up-class is always a user question; down-class (a concept that turns out trivial) is announce-and-execute. The move is one-way, once, and never after tasks are cut.
Class-3 mechanical tell: a bug fix touching files outside its declared blast radius means one of two things — the root cause lives elsewhere (re-audit), or a spec-change is smuggling itself through the bug lane (the trap question, caught mechanically by the scope-drift check).
Anti-staleness (class 2): no delta-story without a cited flow step; no cited flow change without the canonical flows.md (<app>/docs/user_stories/<slug>/) patched in the same Gate-1b pass — bootstrapped from current behavior if it doesn't exist yet. Legacy concepts with no PRD: the delta-story's Given clause records prior behavior — never retro-author PRDs as ceremony.

4 The PRD contract shipped 2026-07-02

The PRD is the entry contract to the whole pipeline. The input contract landed this pass: a provenance rule that makes an honest UNCONFIRMED beat confident filler, because the incentive that rewarded padding is now gone.

Fed by — four inputs, raw intent mandatory
  • Raw human intent (mandatory — the requirement itself)
  • Source docs when they exist (GR/circular, tender sheet, client email, incident)
  • Codebase reality (the agent digs — grounding before a word is written)
  • Clarifying Q&A (extracted from the human, never assumed)
NO-INVENTION rule

Agents contribute structure, gap-detection, and grounding — never requirements. Thin input produces questions back at the human, not a padded document. The Step-4 checklist no longer rewards a non-empty section; padding is now a smell, not a passing grade.

Consumers

manager (primary — /intake-requirement) · architect (read-only, for the four sole-witness sections: Out-of-Scope, Constraints, Domain Terminology, Error Scenarios). No second copy of those sections exists anywhere downstream.

Checklist semantics

Every section is either human-confirmed or explicitly marked UNCONFIRMED — never author filler dressed as truth. Confirmed content reads as ground truth downstream, so a lie in it launders past every gate silently.

6 The fabrication asymmetry — the sole-witness sections are the dangerous ones

Not all fabrications are equal. The most dangerous sections to invent are the ones no downstream artifact carries a competing copy of — Out-of-Scope, Constraints, Domain Terminology. A lie there is uncontradictable, so nothing ever "breaks"; the cost is paid silently and permanently. Each seat has its own worst case.

manager · worst
Invented Out-of-Scope

An exclusion the human never confirmed reads as settled truth — so it suppresses the clarifying questions the manager would otherwise ask. Gate 1 collapses silently; the un-approved interpretation ships through every gate downstream.

architect · worst
Invented constraint

A fabricated "1M rows/day" or "sub-100ms" becomes a fake confirmed change axis: speculative ES read models, caching layers, async pipelines. Structural, silent, unfalsifiable — permanent complexity bought for a change that never comes.

reviewer · mirror
New-module-as-extension

The review-net version of the same shape. A foreign concern welded into a host module fails silent — each PR looks like a reasonable small extension; no one diff trips a threshold. Death by a thousand approved commits.

The asymmetry, stated once: the fabrication that fails loud (extension-as-new-module → duplication, a stranded module, a "why not reuse fee_engine?" flag) is cheap — it gets caught pre-merge. The one that fails silent (invented constraint, invented out-of-scope, new-as-extension) is expensive precisely because it never presents as a violation in any single artifact. The uncontradictable one is always the dangerous one.

7 The bug-fix lane proposed

A defect is a story that already shipped — the acceptance criteria exist and are being violated, so writing new stories is ceremony. It bypasses Gate 1's story machinery, but not the gate's discipline: without a reproduction, the reviewer has nothing to verify the fix against, only "does it run."

The minimal artifact
  • Expected vs actual — cite the spec/story if one exists
  • Reproduction — failing input → wrong output → right output
  • Blast radius — who else consumes this path
  • Root-cause vs symptom — one line, so the fix isn't a None-guard papering over a broken contract
  • Regression test — failing-before / passing-after, proving the fix is load-bearing
The one trap question

Before the fix goes into the bug lane, the manager must ask:

"Is the behaviour wrong per spec, or is the spec changing?"

The second answer reclassifies out of the bug lane — it's an extension in disguise and needs stories, not a patch. Skipping this question is how a spec-change smuggles itself past Gate 1 as a "bug fix."

8 Classification is falsifiable, not authoritative proposed

The reviewer's rule: a declared classification is only useful if it's something the review net checks, never something it trusts as already-true. A fabricated module list launders scope past the reviewer exactly as a fabricated Out-of-Scope launders past the manager. Its value is that it's diffable, not that it's authoritative. Who declares moved with the depth: classes 1/2/4 — the architect writes the declared-modules line at the ADR (Gate 2), after actually reading the code; class 3 — the bug card declares its blast radius at intake (bugs skip Phase B).
