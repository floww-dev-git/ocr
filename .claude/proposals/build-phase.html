SDLC · Phase C

Build & Verify

The inner loop that turns an approved plan into reviewed, integrated, committed code — one task at a time, test-first, with one user gate at the end instead of one per task.

A false "done" is structurally impossible. Every task's failing tests are written FROM its planned Cases: list before any code exists; every ✔ names a real artifact a hook can verify; every task passes an independent review before the plan advances. The loop doesn't trust the builder's claim — it makes the claim checkable at every stage.

1Where the phase sits

Everything left of the loop was approved at Gates 1–3. Everything right of it is delivery. The user touches the build phase at exactly ONE gate — end-of-plan commit+push (◆4). Per-task reviews run every task but only pause the pipeline on Critical/High findings.

Gate 3 ✓ (plan approved) │ ▼ ┌─ per task ──────────────────────────────────────────────────────────────┐ │ ANALYZE → ⟳(RED → GREEN → REFACTOR) per Cases: entry → VERIFY* → SELF-REVIEW → REVIEW → INTEGRATE │ × N tasks └──────────────────────────────────────────────────────────────────────────┘ │ (auto-advance between tasks — commits automatic, no questions) ▼ per task: LOCAL COMMIT (auto, announced) → ◆4 PUSH GATE (commit series + test report, ONE approval) → security† → promote-to-envs → /feature-retro * conditional — artifact tasks only † auto — sensitive paths touched

2The inner loop, station by station

Who runs each stage, what skill drives it, and what mechanically enforces it. Blue dots = developer · red dots = independent seats · green dots = mechanical checks ride along.

ANALYZEdeveloper/process-tasks-list

Read the task line: its Cases: list (authored at planning, AC-traced) and ✔ criterion. The task text is self-sufficient — the ADR is only consulted for WHY, never to decode WHAT.

REDdeveloper/interactor-test-writerCases: = the test list

A LOOP with GREEN/REFACTOR, one cycle per Cases: entry: this case's failing test — written FROM the list, never re-derived from code. Watch it fail for the RIGHT reason. Dependency-first: the task's collaborators are already built (earlier slice tasks) — wire them real; autospec only interfaces. A missing Cases: line is an authoring error → Design Correction, not improvisation.

GREENdeveloper/write-interactor · /write-graphql-*quality-gate.sh

Minimum code that passes — one task only. The matching workflow skill is invoked first (skill gate table in the developer persona). Cross-app imports and framework-in-interactor violations are hook-blocked at write time.

REFACTORdeveloper

On green only: naming, extraction, clean-code limits. Tests stay green.

VERIFY (conditional)developer

Fires ONLY when the deliverable is an artifact unit tests can't assert directly — generated PDF/letter, schema_gen output, CSV export, HTML report. Locate that domain's specific generator, run it, inspect, present. Never blind-glob repo-root notebooks (450+ ops/migration scripts, several destructive). No artifact → one-line skip.

SELF-REVIEWdeveloper/self-review-checklistchecks A–L · L is blocking

Twelve checks from real review history (DRY, cross-app, null guards, truthiness, dead code, scope drift, ConfigIO…). Check L blocks the verdict: every production file has tests AND every Cases: entry has a corresponding test.

INDEPENDENT REVIEWreviewer/review-prsaved → .claude/reviews/

Fresh eyes, 12-item checklist, severity-ranked findings, ends with APPROVED / CHANGES REQUESTED. Emits the ## Escaped Cases section (explicit None) — behavioural misses the Cases: line should have listed. Critical/High → developer auto-fixes via /impl-review-points (no "should I fix?" question) → re-review. 6+ files → review team (2; +security teammate on sensitive paths).

INTEGRATEdeveloper

Full app test suite. Regressions fixed NOW, in this loop — no debt forwarded to the next task.

◆4 · END-OF-PLAN — the PUSH gate: commit series + test report, one approval · then env-promotion checklist (one question)

Path-triggered nudge at this gate: if the plan touched GraphQL/portal surfaces, one line recommends a @scout gamma E2E after merge — a recommendation, never a gate, and explicitly NOT a substitute for review/security.

4Orchestration — who drives what

RuleContract
Two nested loopsManager drives the OUTER pipeline between gates; developer executes the INNER loop per task. Never conflated.
Commit batchingMulti-task plans: NO commit gate between tasks; ONE consolidated gate at end-of-plan. Overrides: user "commit now" · safety valve at 10+ tasks / 30+ files · plan-failure checkpoint (good work never sits hostage to a bad task).
Auto-continueReview findings → developer fixes → re-review, with zero questions asked. The fix cycle shares the original commit gate.
Test ownershipDeveloper authors RED for every active task — the test derives from and drives the implementation ("one continuous thought"). test-writer only for: standalone test tasks · backfill on shipped code · review-team audits.
Review teams6+ files → 2 teammates (Architecture+CleanCode, TestCoverage+EdgeCases); sensitive paths → +Security. The TestCoverage seat is a REVIEWER, never the test-writer (fresh-eyes). Consolidated review saved to .claude/reviews/.
Security triggerAuto after final clean review when the diff touches iam/ payments_engine/ plugins/razorpay/ bps/ tdr/ or new integration adapters.
Design Correction ProtocolDeveloper discovers the plan is wrong → HALT + report (never work around it). Manager fixes PRD/flows/stories; architect fixes ADR/tasks; user approves the delta; developer resumes. Severity maps: cosmetic=batched · design=delta-only approval · structural=Gate-3 re-run for remaining tasks.
Single-writer + fresh sessionsOne writer per shared file; background agents deliver to report files; long plans hand off to a fresh developer session at task boundaries instead of resuming a saturated transcript.
