# Fee & Payment Lifecycle — Core Domain Knowledge

> This is the MOST CRITICAL knowledge file in the payments agent system. Every feature in payments_engine or fee_engine MUST be understood through this lens. Misunderstanding = wrong money.

## Application Types

Two types: **SW (Single Window)** and **IA (Instant Approval)**. Code is 100% application-type agnostic — no `if SW` / `if IA` branches. Both handled by the same configurable fee payment template system. **Every feature must work correctly for BOTH types simultaneously.**

## SW (Single Window) Flow

### Step 1: Processing Fee (Direct Order)
- Applicant submits application
- System creates a **direct order** (`allow_partial=False`, no OCEs, no fee heads)
- Fixed amount: 10k/20k (configurable)
- Applicant pays via Razorpay
- This is the ONLY case of a direct order in the system

### Step 2: Officer Generates Fees
- Application assigned to officer after processing fee paid
- Officer creates fees in **fee_engine** (Entity Fee Rule Set / EFR)
- Each fee head gets an amount (system-calculated or officer-overridden)
- Officer amount takes precedence over system amount

### Step 3: Processing Fee Adjustment
- System tries to adjust the already-paid processing fee (10k/20k) into the generated fee head amounts
- **Distribution logic:** Configured in fee_engine by business team — includes priority order for which fee heads absorb the processing fee first. NOT proportional, NOT officer-decided at runtime
- **Adjustment is NOT guaranteed to be complete:**
  - Fully adjusted: processing fee entirely absorbed into fee heads
  - Partially adjusted: some processing fee left over
  - Not adjusted at all: generated fees too small to absorb processing fee
- **Retroactive OCEs** created on the processing fee order (which originally had no OCEs):
  - Created when EFR transitions to "orders created" status
  - Code: `fee_engine.interactors.fixed_order_adjustments.create_fixed_order_contributed_entities.CreateFixedOrderContributedEntitiesInteractor`
  - These OCEs get `status=PAID` (order was already paid)
  - `oce.amount = adjusted_amount` per fee head
  - Same fee_header_id can appear in BOTH the processing fee order's OCEs AND the new order's OCEs

### Step 4: Orders & OCEs Created
- `fee_head_amount` = system amount OR officer amount (officer takes precedence)
- `adjusted_amount` = processing fee amount previously paid on this fee head (or 0)
- `net_amount = fee_head_amount - adjusted_amount`
- `net_amount` injected into OCEs → forms an order where `order.amount == sum(oce.amount)`
- Order amount is always > 0 (net of adjustments)

### Step 5: Normal Payment Flow
- Razorpay orders created on the order
- Applicant pays (selective OCE payment possible since `allow_partial=True`)
- Consolidation generated
- Reconciliation happens

## IA (Instant Approval) Flow

### Step 1: Auto-Generated Fees (First EFR)
- Fee heads auto-generated by system (NOT officer) when application submitted
- Orders + OCEs created immediately
- **No processing fee, no direct order** in IA flow
- `adjusted_amount = 0` for all OCEs (first payment, nothing paid yet)
- Applicant pays fees BEFORE officer sees the application

### Step 2: Officer Revises Fees (Second EFR)
- After payment, officer gets the application
- Officer generates a NEW EFR (EFR2) which revises the previous fees
- All fee heads paid in first payment get `adjusted_amount` from first payment
- Officer can add NEW fee heads not in first payment (`adjusted_amount = 0`)

### Step 3: Three Scenarios Based on Revised Total vs Paid

#### Scenario A: Revised Fee < Paid Fee (Overpayment)
- Applicant overpaid — revised fees are less than what was collected
- **Action:** Update `OCE.revised_amount` on the INITIAL order's OCEs to reflect new amounts
- The overpaid difference goes into `EXTRA_AMOUNT_PAID` (null fee_header_id) in consolidation
- **NO new order created** — just revised_amount updated on existing OCEs

#### Scenario B: Revised Fee == Paid Fee (Rearrangement)
- Total fee unchanged, but individual fee head amounts may have shifted
- **Action:** Update `OCE.revised_amount` if individual fee head amounts changed
- No overpayment, no new order
- Officer just rearranged the distribution across fee heads

#### Scenario C: Revised Fee > Paid Fee (Remaining Balance)
- Applicant owes more money
- **CRITICAL:** DO NOT touch the previous order's `OCE.revised_amount`
- **Action:** Create a NEW order with ALL fee heads as OCEs, including:
  - Fee heads where EFR2 amount < EFR1 amount → **NEGATIVE `oce.amount`** (overpaid on this specific head)
  - Fee heads where EFR2 amount > EFR1 amount → positive oce.amount (underpaid)
  - New fee heads not in EFR1 → full amount as oce.amount
- **This is where negative OCEs come from**

##### Negative OCE + Effective Amount + Penalty Example
```
EFR1: f1=100, f2=50  (applicant paid 150)
EFR2: f1=50, f2=50, f3=300  (revised total = 400, net = 400-150 = 250)

New order OCEs:
  f1: amount = -50  (overpaid by 50 on this head)
      effective_amount = 0  (setoff: negative absorbed by positive OCEs)
      penalty_amount = 0  (penalty on effective_amount, which is 0)

  f2: amount = 0  (no change)
      effective_amount = 0
      penalty_amount = 0

  f3: amount = 300  (new fee head, full amount)
      effective_amount = 250  (absorbed f1's -50 via proportional setoff)
      penalty_amount = calculated on 250, not 300

Order amount = -50 + 0 + 300 = 250 (what applicant owes)
```

## Where Each OCE Amount Field Comes From

| Field | Set By | When | What It Represents |
|---|---|---|---|
| `amount` | Order creation (fee_engine) | EFR generated | `net_amount = fee_head_amount - adjusted_amount`. Can be negative in Scenario C |
| `effective_amount` | `CalculateEffectiveAmountsInteractor` | After order creation | Setoff-adjusted amount. Negative OCEs → 0, positive OCEs → reduced by proportional setoff. **Used for Razorpay charging** |
| `revised_amount` | Fee recalculation (EFR2) | Scenarios A & B only | Updated fee head amount when revised ≤ paid. **Used for consolidation/refund/recon** |
| `penalty_amount` | Daily cron job | `update_penalties_for_orders_handler` | Calculated on overdue orders. NOT calculated at order creation time |

### Penalty Calculation
- **NOT computed at payment time or order creation** — runs via daily cron: `payments_engine.event_handlers.trigger_handlers.update_penalties_for_orders_handler`
- Stored on `OCE.penalty_amount` field
- Applies to overdue orders based on penalty_config (percentage + grace days)
- For negative OCEs with `effective_amount=0`, penalty would be 0

### Consolidation Math Across EFRs
Both revision paths lead to the same financial result:

**Scenario A/B (revised ≤ paid):** Consolidation sees EFR1 OCE with `revised_amount` set
- f1: `revised_amount=50` → consolidation uses 50

**Scenario C (revised > paid):** Consolidation sees EFR1 OCE (unchanged) + EFR2 OCE (negative)
- f1 in EFR1 order: `amount=100, revised_amount=NULL` → consolidation uses 100
- f1 in EFR2 order: `amount=-50, revised_amount=NULL` → consolidation uses -50
- Grouped by fee_header_id: 100 + (-50) = 50

Both paths → f1 consolidation base_amount = 50. This is by design.

### Critical Rules
1. **Scenario C (revised > paid):** NEVER set `revised_amount` on previous order's OCEs. Create new order instead
2. **Scenario A/B (revised ≤ paid):** NEVER create new order. Update `revised_amount` on existing OCEs instead
3. **Negative OCEs are valid business data** — they represent overpayment on specific fee heads when total is still positive
4. **Zero-amount OCEs can exist** — fee head unchanged between EFRs. Doesn't affect calculations as long as math is correct
5. **Penalty runs daily via cron**, not at order creation — `update_penalties_for_orders_handler`
6. **Consolidation uses `revised_amount ?? total_amount`** — never `effective_amount`
7. **Razorpay charging uses `effective_amount`** — never `revised_amount`
8. **Same fee_header_id can appear across multiple orders** — consolidation groups by fee_header_id across all orders, which is why both paths yield correct totals

## OCE Identity Fields

- `OCE.entity_id` = fee_header_id — this is how consolidation groups amounts per fee header
- `OCE.entity_type` = OrderContributedEntityType enum value
- Same fee_header_id can appear in OCEs across multiple orders (EFR1 order + EFR2 order + processing fee order)

## EFR (Entity Fee Rule Set) Versioning

- EFR1 = initial fee generation (auto in IA, officer in SW)
- EFR2 = officer revision (always officer)
- Multiple EFRs possible per application
- Each EFR generates its own set of orders + OCEs
- Previous EFR's OCEs get `revised_amount` (Scenarios A/B) or stay untouched (Scenario C)
- OCEs are scoped to their parent Order → their EFR

## Processing Fee Adjustment in SW

```
Processing fee paid: 20,000 (direct order)

Officer generates fees:
  fee_head_1: 50,000
  fee_head_2: 30,000
  fee_head_3: 10,000
  Total: 90,000

Adjustment: 20,000 processing fee distributed across fee heads
  fee_head_1 absorbs: 15,000
  fee_head_2 absorbs: 5,000
  fee_head_3 absorbs: 0

OCEs created for new order:
  f1: amount = 50,000 - 15,000 = 35,000 (net after adjustment)
  f2: amount = 30,000 - 5,000 = 25,000
  f3: amount = 10,000 - 0 = 10,000
  Order total: 70,000

OCEs created for processing fee order (retroactive):
  f1: amount = 15,000 (what was adjusted from processing fee)
  f2: amount = 5,000
```

## Cross-Cutting Rules

1. **Code is application-type agnostic** — no `if application_type == 'SW'` anywhere. Both types use the same order/OCE/payment machinery
2. **Every feature must be tested against BOTH flows** — a change that works for IA but breaks SW (or vice versa) is a Critical bug
3. **Fee calculation belongs to fee_engine** — payments_engine NEVER calculates fees. It only receives orders + OCEs
4. **The fee payment template** (in fee_engine) controls the flow — which fee heads, adjustment logic, EFR versioning
5. **`allow_partial` flag** distinguishes direct orders (False) from fee-engine orders (True) — this is the closest thing to "application type" in payments code
